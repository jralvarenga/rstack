These are my rules on how the agent sets up rstack in a project. The goal is that every agent opening the project, in any harness, knows the project uses rstack and which model handles each kind of work, without me repeating it. This skill only writes config. The routing itself lives in [agent-orchestration](../agent-orchestration/SKILL.md), and this skill never keeps its own copy of it.

## Before writing

1. When I ask to install rstack itself, point to the Install section of the [README](https://github.com/jralvarenga/rstack#install). This skill configures a project, not an agent.
2. Find agent-orchestration next to this skill, at `../agent-orchestration/SKILL.md`, or load the installed `agent-orchestration` skill. When it isn't installed, tell me that setup-rstack needs it, and stop. Don't write a stub or a section without the routing.
3. Read its "Routing table" section now, at setup time. Never write the routing from memory, from an earlier setup, or from this skill. When the section is missing or has no rows, say so and stop.
4. Read the project's `AGENTS.md` and `CLAUDE.md`. Look outside the rstack section and in harness config like `.cursor/rules/` or `.claude/settings.json` for rules that choose a model, provider, or reasoning effort. Check what choice each rule governs.

## Existing model rules

Compare each project rule with the rstack row or override for the same choice. A startup model in `.claude/settings.json` can coexist with a model for delegated implementation. Ask me which rule wins only when they prescribe different settings for the same choice.

On refresh, reuse a recorded override when the source rule still matches and maps to the same row. For an older override without a recorded source, add the source when the rule clearly matches the row and the override. Compare the choices again when the source rule or its mapping changes.

- When I choose the project rule, keep it in place and record it as an override with the source file path and rule text.
- When I choose rstack's routing, ask me to approve removing or updating the project rule before writing the routing I chose. When I decline, keep the rule and record or retain its override.

## The rstack section

Write the section between these markers. Edit a project rule outside the markers only when I approve the specific change under "Existing model rules" or "Overrides".

```md
<!-- rstack:start -->
## rstack

This project uses rstack. Start every task from the `rstack-mode` skill, and follow `agent-orchestration` when delegating or picking a model.

### Model routing

Generated by setup-rstack from the routing table in `agent-orchestration` on <date>. Re-run setup-rstack to refresh it instead of editing it by hand. Rows without an override follow `agent-orchestration` when it is installed.

<the routing table>

### Project overrides

- <Task type>: <what replaces the row>. <Why, in one sentence.>
  - Source: <file path and original rule, when keeping a project rule>
<!-- rstack:end -->
```

- Copy the routing table's header and rows as they are in `agent-orchestration`, with the same columns and the same wording. Don't add, drop, rename, or reorder anything.
- Write the date as `YYYY-MM-DD`.
- Leave out "Project overrides" when there are none.
- Include the source line only for overrides based on a project rule.
- Overrides replace the matching row for this project only. Tell the agent to use the override instead of the row by naming the row's task type exactly as the table does.

## Writing AGENTS.md

- When the markers already exist, replace the marked section. Outside it, make only the project rule edits I approved. Running setup again with the same table and overrides gives the same section, apart from the date.
- Keep the existing overrides when you regenerate, unless I ask to change or drop them. When an override names a task type the new table no longer has, ask me whether to remap it to another row or drop it. Follow "Overrides" when dropping it.
- When the markers don't exist, append the section at the end of `AGENTS.md`.
- When there is any marker but not exactly one `<!-- rstack:start -->` and exactly one `<!-- rstack:end -->`, with the start first, stop and ask me how to fix it instead of guessing.
- When `AGENTS.md` doesn't exist, create it following [agent-file](../agent-file/SKILL.md) and put the rstack section in it. When `CLAUDE.md` already holds the project's instructions, follow agent-file's rule for a different source of truth and create `AGENTS.md` with only the rstack section.

## Wiring up Claude Code

- When `CLAUDE.md` doesn't exist, create it with only `@AGENTS.md`.
- When `CLAUDE.md` exists without the import, offer to add `@AGENTS.md` while keeping its instructions. When I decline, report that Claude Code setup is incomplete.

## Overrides

I can override a row for one project, for example "use a different model for implementation here":

- Match the ask to a task type in the routing table. When it doesn't match one, ask which row I mean.
- Record the override under "Project overrides" with what replaces the row and why. Don't edit the copied table.
- When I name a model, write it as I named it. Don't check it against the table or swap it for another.
- Before dropping an override, check its source and look for any project rule that would still override the same row. Ask me to approve removing or updating each such rule. When I decline, keep the override and tell me the project rule still applies.
- When no project rule would still override the row, drop the override. The row, if still in the table, follows `agent-orchestration` again.

## Report

Tell me what you wrote:

- The path of `AGENTS.md`, and whether you created it, added the section, or replaced it.
- That the routing came from `agent-orchestration`, and how many rows it has.
- Every override in the section, and any existing model rule you found and what we decided about it.
- Whether `CLAUDE.md` was created, the import was added or already present, or Claude Code setup is incomplete.

Don't commit unless I ask.
