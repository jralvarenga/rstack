These are my rules on how the agent sets up rstack in a project. The goal is that every agent opening the project, in any harness, knows the project uses rstack and which model handles each kind of work, without me repeating it. This skill only writes config. The routing itself lives in [agent-orchestration](../agent-orchestration/SKILL.md), and this skill never keeps its own copy of it.

## Before writing

1. When I ask to install rstack itself, point to the Install section of the [README](https://github.com/jralvarenga/skills#install). This skill configures a project, not an agent.
2. Find agent-orchestration next to this skill, at `../agent-orchestration/SKILL.md`, or load the installed `agent-orchestration` skill. When it isn't installed, tell me that setup-rstack needs it, and stop. Don't write a stub or a section without the routing.
3. Read its "Routing table" section now, at setup time. Never write the routing from memory, from an earlier setup, or from this skill. When the section is missing or has no rows, say so and stop.
4. Read the project's `AGENTS.md` and `CLAUDE.md`, and look for existing model rules: anything outside the rstack section that names a model, provider, or reasoning effort for the agent, in those files or in harness config like `.cursor/rules/` or `.claude/settings.json`.

## Existing model rules

When the project already has model rules, show them to me and ask which one wins before writing anything:

- The project's rule wins: record it as an override in the rstack section, and leave the original where it is.
- rstack's routing wins: write the section without that override. Edit or remove the original rule only when I say so, never silently.

## The rstack section

Write the section between these markers, and keep everything outside them untouched:

```md
<!-- rstack:start -->
## rstack

This project uses rstack. Start every task from the `rstack-mode` skill, and follow `agent-orchestration` when delegating or picking a model.

### Model routing

Generated by setup-rstack from the routing table in `agent-orchestration` on <date>. Re-run setup-rstack to refresh it instead of editing it by hand. Rows without an override follow `agent-orchestration` when it is installed.

<the routing table>

### Project overrides

- <Task type>: <what replaces the row>. <Why, in one sentence.>
<!-- rstack:end -->
```

- Copy the routing table's header and rows as they are in `agent-orchestration`, with the same columns and the same wording. Don't add, drop, rename, or reorder anything.
- Write the date as `YYYY-MM-DD`.
- Leave out "Project overrides" when there are none.
- Overrides replace the matching row for this project only. Tell the agent to use the override instead of the row by naming the row's task type exactly as the table does.

## Writing AGENTS.md

- When the markers already exist, replace everything from `<!-- rstack:start -->` to `<!-- rstack:end -->` and nothing else. Running setup again with the same table and overrides gives the same section, apart from the date.
- Keep the existing overrides when you regenerate, unless I ask to change or drop them.
- When the markers don't exist, append the section at the end of `AGENTS.md`.
- When there is only one marker, more than one rstack section, or the markers are out of order, stop and ask me how to fix it instead of guessing.
- When `AGENTS.md` doesn't exist, create it following [agent-file](../agent-file/SKILL.md), including `CLAUDE.md` with the `@AGENTS.md` import, and put the rstack section in it.
- When `AGENTS.md` exists but `CLAUDE.md` doesn't, create `CLAUDE.md` with `@AGENTS.md`. When `CLAUDE.md` exists without the import, mention it in the report and leave it alone unless I ask.

## Overrides

I can override a row for one project, for example "use a different model for implementation here":

- Match the ask to a task type in the routing table. When it doesn't match one, ask which row I mean.
- Record the override under "Project overrides" with what replaces the row and why. Don't edit the copied table.
- When I name a model, write it as I named it. Don't check it against the table or swap it for another.
- Removing an override drops its line and the row goes back to `agent-orchestration`.

## Report

Tell me what you wrote:

- The path of `AGENTS.md`, and whether you created it, added the section, or replaced it.
- That the routing came from `agent-orchestration`, and how many rows it has.
- Every override in the section, and any existing model rule you found and what we decided about it.
- Whether `CLAUDE.md` was created, already imports `AGENTS.md`, or doesn't.

Don't commit unless I ask.
